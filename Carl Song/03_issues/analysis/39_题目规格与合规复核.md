# 39 · 题目规格、合规复核，与「点 1 只有一条 mmad」的闭式结论

> 日期：2026-10-05（第 4 轮）
> 触发：用户提供了**题目规格**（此前反复索要的 `npu_cases.json` **确实拿不到**，用户明确「没有其他更多的信息了」）
> 结论：**规格给了"形状空间"，没给"15 个具体形状"**；但它给出了一条足够硬的推论 —— **小 M 工况必然存在，且它们的耗时 100% 是固定开销**。

---

## §1 · 规格原文（用户提供，作为硬契约存档）

1. **芯片**：Atlas A3（910C）
2. **维度**：2 维输入；`M ≥ 1`、`N ≥ 1`、`K ≥ 1`；`x1` 固定不转置 `(M,K)`，`x2` **固定已转置** `(N,K)`；不支持空 Tensor，仅支持连续 Tensor
3. **数据类型**：`x1`/`x2` = INT8；`x1Scale`/`x2Scale` = FLOAT32；输出 `y` = INT8，`yScale` = FLOAT32
4. **舍入**：就近偶数舍入（**rint**），**先 round 后 clamp 到 `[-128,127]`**；`rowMax = 0` 时 `yScale = 1.0`、对应行 `y` 全为 0

> ★ 注意第 2 条：**只有下界，没有上界**。这是本规格信息量最大的一句话。

## §2 · 合规复核（对当前 v20 逐条核对）

| 规格条目 | 当前实现 | 位置 | 判定 |
|---|---|---|---|
| 就近偶数舍入（rint） | `QmqQuantizeNearHalf` 用位级判等：`thresholdMantissa = 2·halfMantissa + ((lowerInteger & 1) == 0 ? 1U : -1)` —— 正是「平局取偶」 | `kernel.asc:120-157` | ✅ 一致（**精度红线，不动**） |
| 先 round 后 clamp `[-128,127]` | round 在 `QmqQuantizeNearHalf`；饱和由 `QmqCorrectDiv` 的残差/校正块承担；**ReLU 在前**（`Maxs(fp32Local, ·, 0.0f)` 在 679 / 746） | `kernel.asc:218`、`:679`、`:746` | ✅ 一致 |
| `rowMax = 0 ⇒ yScale = 1.0` | `if (rowMaxLocal.GetValue(row) <= 0.0f) rowScaleLocal.SetValue(row, 1.0f);` | `kernel.asc:597-601` | ✅ 一致 |
| `rowMax = 0 ⇒ 该行 y 全 0` | 量化分支有 `if (rowMaxPrefetch[row] > 0.0f)` 守卫，`rowMax=0` 时整行跳过 | `kernel.asc:682` | ✅ 一致 |
| ReLU | `Maxs(fp32Local, fp32Local, 0.0f, alignedN)` | `kernel.asc:679`、`:746` | ✅ 一致 |
| `x2` 已转置 `(N,K)` | `matmulObj.SetTensorB(x2Gm[0], true)`（`true` = 需转置读） | cube 函数内 | ✅ 一致 |
| 连续 Tensor、无空 Tensor | 全程 `DataCopyPad` + 线性偏移，无 stride 分支；且规格保证 `M,N,K ≥ 1` ⇒ **不需要零尺寸分支** | 全文 | ✅ 一致 |
| `N` **无上界** | `for (nOffset = 0; nOffset < n; nOffset += kVectorTileN)` ⇒ `N > 6144` 自动分多轮，`currentN = min(6144, n-nOffset)` | `kernel.asc:502`、`:615` | ✅ 一致 |
| `M` **无上界** | `for (rowOffset = 0; rowOffset < localRows; rowOffset += kVectorTileRows)` | `kernel.asc:846` | ✅ 一致 |

**⇒ 规格没有引入任何合规缺口。v20 15/15 是通过的，这条复核只是把它与题目契约对齐存档。**

## §3 · 规格真正改变了什么

### 3.1 形状空间：`M,N,K ∈ [1, ∞)`

之前我一直在追「15 个点的具体形状」。**规格说明它拿不到，而且——从规格本身就能推出一条足够用的结论。**

因为我们**自己的形状探针**（v17c）已经把 15 个点分成三段：

| 分段 | 点数 | 点号 |
|---|---|---|
| `m ≤ 16` | **2** | **1, 2** |
| `16 < m ≤ 384` | 7 | 3, 4, 5, 7, 11, 14, 15 |
| `m > 384` | 6 | 6, 8, 9, 10, 12, 13 |

而规格说 `M ≥ 1` ⇒ **`m ≤ 16` 这一小 M 角落在空间里必然非空**，且实测**确实有 2 个点**（1、2）。
⇒ **不需要知道其余 13 个形状，就能锁定这 2 个点的性质。**

### 3.2 小 M ⇒ 只有 1 个核在干活（闭式）

`mBlock 总数 = ceil(m/16)`；`M ≤ 16 ⇒ mBlock 总数 = 1`
⇒ `mBlocksPerGroup = ceilDiv(1, 24) = 1`、`groupCount = ceilDiv(1, 1) = 1`
⇒ **整个 kernel 只有 1 个 AIC + 它配对的 1 个 AIV 在工作，另外 22 个核全程空闲。**

这条解释了为什么点 1（M=4）与点 2 行为相近：**它们不是"算得慢"，而是根本没有并行度可用。**

## §4 · ★★ 决定性算数：点 1 的全部乘加 = **一条 mmad 指令**

点 1 = `(M=4, N=8, K=16)`（唯一已知形状）。
910C 的 Cube 是 `16×16×16` 分形：`M=4 ≤ 16`、`N=8 ≤ 16`、`K=16 ≤ 16` ⇒ **整个矩阵乘恰好落在 1 个分形内 = 1 条 `mmad`**，耗时**几十 ns** 量级。

但它实测 **16.28 µs**（参考实现 T = **2.150 µs**，比值 7.57×）。

> **⇒ 16.28 µs 里与"矩阵乘"有关的部分 ≈ 0。约 14 µs 是纯启动 / 搬运 / 同步 / 量化外壳。**

### 4.1 这 14 µs 值多少分（按评分公式逐档算）

评分 `S = 100/(1+log₁.₅(t/T))`，本工程总分 = 15 点等权平均。

**点 1**（现 `t=16.28`，`T=2.150`，现得分 **16.69**）：

| 若 `t` 降到 | 得分 | **总分增益** |
|---|---|---|
| 2.15（=T） | 100.0 | **+5.55** |
| 3.00 | 54.9 | **+2.55** |
| 4.00 | 39.5 | +1.52 |
| 5.00 | 32.5 | +1.05 |
| 16.28（现状） | 16.69 | 0 |

**点 2**（现 `t=10.28`，`T=1.769`，现得分 **18.73**）：

| 若 `t` 降到 | 得分 | **总分增益** |
|---|---|---|
| 1.77（=T） | 100.0 | **+5.42** |
| 2.50 | 54.0 | **+2.35** |
| 3.50 | 37.3 | +1.24 |

### 4.2 与既有杠杆的对照

| 动作 | 总分增益 |
|---|---|
| **只把点 1 从 16.28 → 3.0 µs** | **+2.55** |
| **只把点 2 从 10.28 → 2.5 µs** | **+2.35** |
| 两者合计（保守到 3 µs 附近） | **≈ +4.9** |
| 对照：v20 全部改动（`CFG_MDL`） | +0.69 |
| 对照：**全 15 点提速 30%** | +5.27 |
| 对照：把 F 从全 15 点扣掉 10 µs | +11~13 |

**⇒ 只打两个点，就能拿到 v20 的 3.5 倍、接近"全点提速 30%"。这不是微优化，这是主战场。**
**⇒ E24′ 至此有了两个具体承载点，不再是抽象的"杠杆表"。**

## §5 · 路线重排（P0 内部再排序）

`M ≤ 16 ⇒ 1 核` 这条闭式把 P0 的目标从"平均摊薄"变成"**打掉那条串行链上的每一段**"。当前串行链（按嫌疑排序）：

| 序 | 候选开销段 | 依据 | 消除手段 | 风险 |
|---|---|---|---|---|
| **0** | **host 侧 `run_kernel` 内代码**（tiling 计算、对象构造、`aclrtSynchronizeStream`） | `analysis/19` 说"可能计入"，**但唯一依据 2.74 µs 已被 E25 判为噪声 ⇒ 无定论** | **H2 tiling 缓存**（位相同、零精度风险）；再试去 `aclrtSynchronizeStream` | 低（前）／中（后，E19） |
| **1** | **AIC 侧 `REGIST_MATMUL_OBJ` + `Matmul::Init` + 每个 mBlock 的 `SetOrgShape/SetTail/SetTensorA/SetTensorB`** | v18 证明 AIV 侧准备 <1 µs ⇒ 14 µs 不在 AIV；**AIC 是剩余主嫌** | **P0-b：去高层 `Matmul`，改 cube 原语**（直接 L1→L0A/L0B + 1 条 `mmad` + fixpipe） | 高（重写量大、API 不可本地验证 = E19） |
| **2** | **GM workspace 往返**：`IterateAll(workspaceGm)` → AIV 再读回 | `M ≤ 16` 且 `N` 不大时整个 C 只几百字节～几 KB，**本可留在 UB** | 小 N 走 UB 直出，跳过 GM | 中 |
| **3** | **跨核握手**：`CrossCoreSetFlag/WaitFlag` 自旋 | 1 个 AIC 对 1 个 AIV，握手本身应有意义；但自旋轮询的固定代价未知 | 小 M 时考虑单核完成（AIC 直接干完） | 中 |

**⇒ 建议顺序（每步单独提交、单独验证，符合 E19/E26）：**

| 步 | 动作 | 主要验证 |
|---|---|---|
| **1** | **P0-a：H2 tiling 缓存**（host，位相同） | 若点 1/2 **明显**变快 ⇒ **host 计时成立**，立刻把 P0 全部押在 host 侧；若毫无变化 ⇒ host 不计时，转 AIC（第 2 步） |
| **2** | **P0-b：去高层 `Matmul`，改原语 + 单 mmad 直出** | 针对 AIC 启动段，预期对点 1/2 是 **>50%** 量级 |
| **3** | 小 N 走 UB 直出，跳过 GM 往返 | 针对第 2 号嫌疑 |
| 并行 | **P1（2D 核网格）** | 只救 `16 < m ≤ 384` 的 7 个点；**对点 1/2 无用**（M ≤ 16 时 N 切分才有效，而 N 可能只有 8） |
| 并行 | P2 继续 cube 配置族 | 小步累积 |

> ⚠️ **重要修正**：此前把 P1（N 切分）当作救 `m ≤ 384` 的 9 个点的手段。
> 现在按规格看：`m ≤ 16` 的点（1、2）**能不能被 N 切分救，取决于 N 有多大**（点 1 的 N 只有 8 ⇒ 切不动）。
> ⇒ **P1 的有效区间是 `16 < m ≤ 384` 那 7 个点**，小 M 的两个点只能靠**砍固定开销**。

## §6 · 形状问题：仍然无解，但**不再阻塞**

- **能拿到的**：形状**空间**（`M,N,K ≥ 1`，无上界）、1 个精确锚点 `(4,8,16)`、15 个点的 **m 三段分区**、15 个 `T` 值。
- **拿不到的**：其余 14 个 `(M,N,K)`。
- **唯一剩余获取途径**：在 `run_kernel` 里加 `AscendC::printf` 打印 `m/n/k` 后提交一次（**新增 API，不可本地验证 = E19；且耗一次提交机会**）。
  ⇒ **建议暂不做**：§4 的结论已经说明，**不依赖具体形状也能推进 P0**，而 P0 的收益上限高于 P1。等 P0 打完再回来看是否还需要。
- **设计原则（替代"知道形状"）**：**做成形状自适应**，即不论 `M/N/K` 落在哪里都走对路径 —— 这正是 §5 第 1、2 步（host 侧与 AIC 侧启动段）天然具备的性质。
