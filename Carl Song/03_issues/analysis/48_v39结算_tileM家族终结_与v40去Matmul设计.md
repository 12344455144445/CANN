## 三、★ 本轮把四条候选路**逐条否掉**（查台账 + 读热循环）

### 3.1 ✗ 精简 `PipeBarrier<PIPE_V>` —— **已被实测否证（v8/v10）**

`analysis/26`：**v8 删 2 处、v10 删 4 处**，两次提交的逐点结果差异 **< 1.5%**，总耗时只差 1.63%，**总分 19.1325 → 19.1325（±0.000）**。
原文结论：「`PipeBarrier<PIPE_V>()` 在 910C 上被硬件/编译器有效隐藏，其开销远小于按 150 cycle 估算的值。」
（另：`analysis/02` 记载 v8 还因删掉 `ReduceMax` 后的屏障引入了**标量读旧值的正确性 bug**。）
**⇒ 永久关闭，不再尝试。**

### 3.2 ✗ host 侧（含 `GetTiling` 缓存）—— **已被实测否证（v21）**

`analysis/38` §3.1 记载：`PATCH-H1`（workspace 缓存）+ `PATCH-H2`（tiling 缓存）实测只值 2.74 µs，**总分 +0.41%（噪声内）**。
**⇒ 「用时不计 host」这一结论成立（双重证据）。永久关闭。**

### 3.3 ✗ 优化 Pass-1 的逐行标量回读（D 路由的原目标）

代码注释（第 707 行）自述：**「Pass-2 承担整算子约 83% 的向量计算量」**，且 Pass-1（575~645）与 Pass-2 都已在 `[OPT-V13]`/`[OPT-V14]` 里按 `kPrefetchSpan = 64` 行一组做过标量预取。
**⇒ Pass-1 的全部优化上限只有 ~17% × 串行化比例 ⇒ 远不及 0.6 分门槛。不做。**

### 3.4 ✗ Pass-2 的**指令条数** —— 已接近算法下界

Pass-2 内层每行每 N 分片必须执行：
`Cast → Muls → Mul → Maxs → DataCopy → Duplicate → QmqDiv → Cast → Cast → Adds → Sub → Abs → [近似半屏判别] → Maxs → Mins → Cast → Cast → Cast → DataCopyPad`
—— 其中 `QmqDiv`/`QmqCorrectDiv`/`QmqQuantizeNearHalf` 是**精度红线（逐字节不可改）**，其余每条都是语义必需。
**⇒ 没有可删的向量指令。只能换结构（把「两遍读 C」压成一遍或换掉取数方式），那是重写量级。**

## 五、v40 设计：**小形状彻底绕开 AIC 的 `Matmul` 全程**

### 5.1 思路

`Matmul::Init` 的成本**与形状无关**。既然如此，就不要试图"摊薄"它，而是**在小形状上根本不要它**：

```
m·n·k ≤ 4096 且 k ≤ 64 且 m ≤ 64 且 n ≤ 64   ⇒   走「AIV 自算」路径
```

* **AIC**：`quant_matmul_relu_quant_cube` 的最前面直接 `return`（**不发任何 flag**，也**不构造 `TPipe`/`Matmul`/`Init`**）⇒ 8~9 µs 直接消失；
* **AIV**：同一个判定成立时**跳过 `CrossCoreWaitFlag`**，改为自己从 `x1`/`x2` 算出 C 并写进 `workspace`，随后**原封不动**执行既有的 Pass-1 / Pass-2（它们本来就是从 `workspace` 读 C 的）；
* **不满足判定的形状**：两边都逐字节等价于 v39 ⇒ **天然对照组（E26/E69）**。

### 5.2 ★ 为什么 C 可以逐位相同（关键论证）

`x1`/`x2` 是 **int8**，乘积 `|a·b| ≤ 127×127 = 16129`（fp32 精确），
累加上界 `|Σ_k a·b| ≤ k×16129 ≤ 64×16129 = 1.03e6 < 2²⁴`（**fp32 可精确表示每一个中间和**）
⇒ **无论用什么次序、什么归约树把每一项加进来，结果都是同一个整数**，与 cube 用 int32 累加得到的 C **逐位相同**。
（⇒ 与 cube 路径的位级等价**可证**，`y` 的 `tol=0` 不会成为障碍。）

### 5.3 落点（相对 v39 的 4 处改动）

1. **新增判定函数**（放在 `QmqAlignUp` 之后，`__aicore__ inline`）：
   ```cpp
   __aicore__ inline bool QmqTinyShape(uint32_t m, uint32_t n, uint32_t k)
   {
       const uint64_t macs = static_cast<uint64_t>(m) * n * k;
       return (m > 0U) && (n > 0U) && (k > 0U) && (k <= 64U) &&
              (m <= 64U) && (n <= 64U) && (macs <= 4096ULL);
   }
   ```
   （`k ≤ 64`、`m,n ≤ 64` 同时把 AIV 侧的 UB 用量钉死在 `64×alignUp(64,8) = 4608` 个 float 以内，
   刚好能**复用已有的** `fp32Buffer` / `halfBuffer`（各 6144 float）作暂存 ⇒ **不新增任何 UB**。）

2. **AIC 提前返回**：在 `quant_matmul_relu_quant_cube` 的 `if (firstMOffset >= m) { ... }` 块**之前**插入
   ```cpp
   // [OPT-V40] 小形状：AIC 完全不参与（不构造 TPipe/Matmul、不调 Init、不发 flag）
   if (QmqTinyShape(m, n, k)) {
       return;
   }
   ```

3. **AIV 自算 C**：`quant_matmul_relu_quant_vector` 的形参表末尾追加 `GM_ADDR x1, GM_ADDR x2, uint32_t k`；
   在 12 次 `InitBuffer` 之后插入
   ```cpp
   const bool tiny = QmqTinyShape(m, n, k);
   if (tiny) {
       QmqVectorComputeC(x1, x2, workspace, m, n, k, rowStart, rows);
       PipeBarrier<PIPE_ALL>();          // UB→GM(MTE3) 写完成后才能 GM→UB(MTE2) 读回
   }
   ```
   `QmqVectorComputeC` 的算子序列（全部落在**已有**的 `fp32Buffer`/`halfBuffer`/`reduceBuffer` 上）：
   ```
   1. DataCopyPad : x1[rowStart..rowStart+rows) 的 rows×k 个 int8  →  int8 暂存
   2. Cast        : int8 → half → float           （与既有 Cast 路径同族）
   3. DataCopyPad : x2 的 n×k 个 int8             →  int8 暂存
   4. Cast        : int8 → half → float
   5. 逐 (i, j)   : Mul(prod, x1f[i], x2f[j], kAligned)
                    ReduceSum(s, prod, work, kAligned)
                    C[i][j] = (int32) s         ← 标量写回（见 §5.4 备选）
   6. DataCopyPad : C 的 rows×n 个 int32 → workspace GM
   ```

4. **AIV 跳过 flag 等待**：把 `for (localTile ...)` 里的
   `if (localTile == 0U) CrossCoreWaitFlag<2, PIPE_FIX>(kCubeToVectorFlag); else ...`
   改为 `if (!tiny) { ...原样... }`。

### 5.4 ★ 实施前必须解决的两个未知（**这是它今天没能直接提交的原因**）

1. **`Cast` 的合法源类型**：`int8 → float` 是否支持一步？若不支持，走 `int8 → half → float`（两级）。
   本工程的既有代码**只验证过** `Cast(fp32, int32, CAST_RINT)` 与 `Cast(half, int32, CAST_NONE)`、`Cast(int8, half, CAST_RINT)`，
   **没有** `int8 → *` 的实例 ⇒ 这是第一次使用，**本地无 CANN 无法验证**（E19）。
   *降低风险的办法*：先用一次**只做「读 x1 头 16 个元素 → Cast → 写回 yScale 头 2 个元素」的探针**验证 cast 链能编译能跑。
2. **同核 GM 写→读的可见性**：`MTE3` 写 `workspace` 后由 `MTE2` 读回，除 `PipeBarrier<PIPE_ALL>()` 外是否需要 `DataCacheCleanAndInvalid`。
   *备选（可完全绕开该问题）*：**不写 workspace**，而是把 C 直接留在 UB，让 `QmqEnqueueWorkspaceTile` 改为「UB 直通」——但那是更大改动，先不用。

### 5.5 收益 / 风险

* **预期**：命中点（很可能是点 1/2/3 —— 点 1 的形状 `(4,8,16)` 已知，`m·n·k = 512 ≤ 4096` ✓）
  的 `O` 从 ~10.4 µs 降到 ~1.5~2.5 µs，净减 ~4~6 µs：
  | 点 | t 现在 | t 预期 | S 现在 | S 预期 | ΔS |
  |---|---|---|---|---|---|
  | 1 | 11.09 | ~6.5 | 19.50 | ~28.7 | **+9.2** |
  | 2 | 10.46 | ~6.0 | 18.58 | ~24.9 | **+6.3** |
  | 3 | 11.49 | ~6.6 | 21.09 | ~28.4 | **+7.3** |
  ⇒ 三点共 **+22.8 ΔS ⇒ +1.52 分**（⇒ ~24.6）；若顶点更彻底 ⇒ 到 25。
* **风险**：**集中在新增的 `Cast`/`ReduceSum` 链**。首次提交大概率编译不过 ⇒ 需要 2~4 轮平台往返。
* **兜底**：判定不成立的形状逐字节 = v39 ⇒ **最坏结果 = 与今天打平**，不会更慢。

### 5.6 ★ 为什么这条路的第一版就要"读数即探针"

本版不需要任何额外提交来探形状：**命中点会明显变快、未命中点逐字节不动**，
所以一次提交同时给出「点 1/2/3 是否都在判定内」+ 实际增益。

## 六、结论

* **今天净增 +1.03 分（22.04 → 23.07/23.11），`tileM` 家族 + 四条候选路全部走到尽头。**
* **25 分的唯一通路 = 把 `Matmul` 从核函数体里拿掉**（`O: 10.4 → ≤6 µs`）。
  按 §5 的设计，**第一步只需让「小形状」绕开它，就值 +1.5 分**；要拿满，则需把 cube 侧整体换成
  `DataCopy`(GM→L1) → `LoadData`(L1→L0A/L0B) → `Mmad` → `Fixpipe`(L0C→GM) 的手写通路。
* **下一步 = 实现 §5**，并接受 2~4 轮编译往返的成本（E19：本地不可验证 ⇒ 必须单独成版）。
