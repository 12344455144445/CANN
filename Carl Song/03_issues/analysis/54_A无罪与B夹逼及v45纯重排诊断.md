## 三、★★ 元凶夹逼：只剩 B

三条推理合起来把候选夹死：

| # | 事实 | 排除掉谁 |
|---|---|---|
| ① | v42 = v40 + A + B + C ⇒ +17.85%（4381.50 µs，与首测差 0.336% ⇒ 可复现） | — |
| ② | v44 = v40 + A ⇒ **落快簇**（3690.41 µs） | ❌ **A 排除** |
| ③ | C 只作用于 `N ≥ 2048` 的 6 个点；而 C **完全不碰**的高组 6 点回归更多（`k` 1.153 vs 1.116） | ❌ **C 不能解释高组的回归** |

⇒ **唯一的非 C 候选本来就只剩 B；现在 A 也被排除 ⇒ 元凶 = B（合并两个逐行标量循环）。**

### ★ 但这里有一个必须正视的悖论

`quant_matmul_relu_quant_vector(...)` 是在**每个 mBlock** 调用一次的，而 `mBlocksPerGroup ≤ 2` ⇒
**B 那段代码每核最多执行 2 次**。一个「每核跑 2 次」的标量循环怎么可能贡献 **+660 µs**？

⇒ **B 的代价不可能来自它自己的循环体**。它只能来自**它改变了别的东西**。而 B 相对 v40 只有两处相对顺序变化：

```
       第一个行循环   PipeBarrier   AllocTensor   第二个行循环
v40 :      ①            ②            ③              ④
v42 :      —            ③           ①           （与①合并）
                 ↑ 合并后要往 yScaleLocal 写值 ⇒ 合并【必须】先把 AllocTensor 提到循环之前
```

**(i)** `AllocTensor` vs 第一个行循环（v40：循环在前；v42：`AllocTensor` 在前）
**(ii)** `PipeBarrier` vs `AllocTensor`（v40：barrier 在前；v42：barrier 在后）

★ **B 的两半不可分离** —— 合并循环必须先把 `AllocTensor` 提前，所以「合并」与「提前」是一件事。
**能做的分离只有一个**：保留两处顺序变化，但**不合并循环**（见 §四）。

## 四、★ v45 = 纯重排诊断（`v40 + B1`）

### 4.1 设计

```
       第一个行循环   PipeBarrier   AllocTensor   第二个行循环
v40 :      ①            ②            ③              ④
v45 :      ②            ③            ①              ④        ← 只把 ③ 挪到最前
```

即在 v40 上**只把 `LocalTensor<float> yScaleLocal = yScaleQueue.AllocTensor<float>();` 这一行上移 6 行**，
两个行循环保持独立、内容一字未改。它复刻了 B 的 (i)(ii) 两处顺序变化，但**不含合并**。

### 4.2 ★ 这是本工程第一例「纯重排」候选

`ref/make_v45.py` 的 **A12** 断言：**活代码行的多重集与 v40 完全相同**（删除集 = 新增集 = 空集）。
`livecode_diff(v40→v45)` 也只报出一对 insert/delete，且是**同一行文本**：

```
[insert] A行 527..526 -> B行 527..527   + LocalTensor<float> yScaleLocal = yScaleQueue.AllocTensor<float>();
[delete] A行 533..533 -> B行 534..533   - LocalTensor<float> yScaleLocal = yScaleQueue.AllocTensor<float>();
```

★ 这使结论的解释达到最干净的程度：**同一组代码，只换顺序 —— 若结果变慢两位数百分比，那「顺序」本身就是被控变量。**

## 五、★ 副产物：v44 又一次证明「总分 ≠ 总耗时」

v44 的**总耗时全项目最低**（3690.41 µs，比 v40 历史低 0.416%），但**总分反而低 0.1523**（23.2295 < 23.3818）。

原因：得分的边际价值 `dS/dt ∝ S²/t` —— **小 `t` 的点每 1 µs 值钱得多**。v44 的收益集中在
`t` 很大的点（11/12/13/14/15 各快 0.6~1.7%），而 4/5 两点反而慢了 +5.1% / +5.6%（`T` 只有 8.46 / 8.28、
`t/T ≈ 2.6` ⇒ **弹性最高的一段**）⇒ 净亏。

⇒ **E98 的又一实例，且这次更极端：总耗时下降 ≠ 分数上升。**
**纪律**：任何改动都必须按「**逐点 + 边际价值**」判收益，绝不能用总耗时代替（判读时先算
`Σ Δ(1/t_i) · S_i²`，再看两个方向有没有互相抵消）。

## 七、若支 α 成立：新方向（这才是今天真正想拿到的东西）

「同一组代码、只换顺序 ⇒ ±17.85%」一旦成立，会立刻改写对 E100 的理解：

1. **过去所有「等价改写」的读数里都混着「顺序」这一项** —— 包括失败的 v41 / v43 / v42，
   也包括成功的 v35 / v39。⇒ 需要复查的关键结论：v43「删 16 条 barrier = 0 收益」很可能是
   「删 barrier 的收益」与「行序变化带来的代价」**正好抵消**。
2. ★ **Pass-2 行体代价的可控变量不是「指令条数」，而是「指令 / 同步的排布顺序」**
   ⇒ 25 分的攻击面从「**删减**」改为「**重排**」：
   - 把 `PipeBarrier<PIPE_V>` 在行体内**前移或后移**若干行（内容不变、只换位置）；
   - 把行体开头标量预取块（v13/v14）与 `Cast` / `Muls` 的相对位置互换；
   - 把两个 `Cast` 链（`fp32→half→int8`）的位置在行体内前后调整。
3. **实验设计**：全部做成「纯重排」提交（A12 保证多重集不变），并且**一次提交内自带形状对照**
   （门控到 `currentN < 2048`）⇒ 同档位内自带实验组 6 点 + 对照组 9 点，任何档位下都可判读。

> ⚠️ 若支 α 成立，**不要去「修」v45**（把 `AllocTensor` 移回去只是回到 v40）；
> 要把这次读数当作**一把标尺**，去度量「顺序」这个新变量。
