## v138：资源、边界和生命周期

新分支只接受 `32<=N<=8192 && N%32==0`，并且原向量入口已经保证正行数。`floor(8192/N)` 至少为 1，每批行数不超过 256，每批元素数不超过 8192。各行 GM/UB 基址和扁平 INT8 输出都满足 32B 对齐；量化比较补齐到 64 元素，额外残差 lanes 在 Compares 前清零。尺度比较、mask 容量和 tensor 容量不互相越界。

独立枚举 N 为 32..8192 的所有 32 倍数、local rows 为 1..1024，共 262144 个组合，复核显式 UB 公式：

`17*tensorCapacity + 4*N + 12*scaleCapacity + 128 + align32(tensorCapacity/8)`。

峰值为 173952 B；加入已有 Select API 8192 B 预留，共 182144 B，小于 196608 B。`residentRowScale[256]` 为另外的 1024 B 标量数组，实际编译器放置及栈开销尚未由 CANN 编译确认。这个 UB 上界只对应源码显式分配及已列 API 预留。

新 helper 在原 fallback 的 TPipe 创建之前分流，两个分支不会同时分配。INT32 输入完成 Cast 后才重用为尺度 scratch、再重用为量化 quotient；FP32 激活保存在独立 bank。列尺度 bank 在整个 block 循环中只读；输出/尺度队列释放前已完成其对应读写提交。逐批处理保持原 AIV 行归属，没有把单行最大值错误地缩成列片段最大值。

两次 FP32 缩放的顺序、原尺度精修函数和 Div/近半值精修/夹紧/ODD→RINT 链保留。CPU 调度模型支持该设计的有限输入等价性，不能证明 A3 指令精度、NaN/Inf 全部行为、CANN 编译、queue 事件的真实生成或实际收益。Depth1 输入与逐批尺度精修可能抵消减少搬运的收益，这属于尚未测量的性能风险。

## v139：空间布局和同步

新增路径将 C 的写入划分为 M 行块和 N 列块：A 偏移为 `rowOffset*K`，物理 `[N,K]` B 偏移为 `columnOffset*K`，C 起点为 `rowOffset*N+columnOffset`。B 的模板、host tiling 和运行时均使用转置标志；`SetOrgShape(m,n,k,k,n)` 显式维持完整 C 的 N 行跨度。官方五参数定义将 `orgKc` 用作输出 C 的 N，且要求在设置张量之前调用；源码顺序符合这一要求。[官方 SetOrgShape 文档](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/API/ascendcopapi/atlasascendc_api_07_0651.html)

网格预算同时限制 AIC 和 `AIV/2`，host 只在至少两个列分区、网格不超预算以及返回 tiling 的 singleCoreM/N 与请求一致时启动。各已启动核心都到达同一个无条件 `SyncAll<false>()`，没有 return/continue 跳过屏障。AIC 的 IterateAll 和 End 在屏障之前；AIV 完整行处理在屏障之后，零行 AIV 也先参与屏障。官方硬同步支持 A3 混合核心、默认全流水同步，并要求逻辑核数不超过物理可用核；源码采用 `__schedmode__(1)` 对应文档建议的 batch 模式。[官方 SyncAll 文档](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/API/ascendcopapi/atlasascendc_api_07_0204.html)

上述结构没有明显的源码级屏障遗漏。仍未验证真实 mixed launch 排程、Matmul 部分 N 输出跨度、库工作区使用、编译器支持和分支覆盖。完整硬屏障会等待全部 Cube 工作完成，原来的跨 M tile 搬算重叠可能减少；仅“一次 launch”无法证明端到端速度提升。

## 明确的共享限制

两候选都继承原版静态 workspace cache。`QmqAcquireWorkspace` 在容量不足时实际调用 `aclrtFree`，没有跨线程互斥，也没有按 stream/device 隔离。两个线程同时调用时，另一个调用可能仍在使用旧地址，因此原注释“不会主动释放，故不存在 use-after-free”不适用于并发场景。它是继承问题，不是这两个新增分支专有缺陷；当前审查结论仅覆盖串行竞赛调用。审查报告中已有该并发限制，应在公共说明继续保留。
