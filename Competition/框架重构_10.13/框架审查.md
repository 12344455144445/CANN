## 两项主要框架改动

### v138：按片上容量分批驻留完整行

原通用流程先完整扫描 C 求每行最大值，然后重新读取 C、重新 Cast 和执行两次反量化乘法，最后量化。v138 每批保留完整行的 FP32 反量化结果，先求该批独立尺度，再直接量化驻留激活。每个元素减少一次 C 的 GM 读取、一次 Cast 和两次缩放乘法；同时省去旧激活 UB 复制。没有省略必须的整行归约。

适用范围为 `32 <= N <= 8192 && N % 32 == 0`。批行数由 `min(localRows, floor(8192/N))` 推导，支持任意正的局部行数；其余路径保留 v124。动态分配发生在旧 TPipe 创建之前，两种 UB 布局不会同时存在。

资源与生命周期复核：四个 FP32 容量 bank 与一个 INT8 输出合计 `17*T`，加列尺度 `4*N`、三组行级存储 `12*R`、标量归约输出 128 字节和对齐掩码。`T=align64(batch*N)`、`R=align64(batch)`，显式最大 173952 字节；额外计入 8192 字节 API 预留后为 182144，小于本轮 A3 UB 196608。输入 INT32 最后一次读取之后，才借用其 bank 做尺度 scratch 和量化 quotient；原 FP32 激活一直保留在不同 bank。输出、行尺度和输入队列按批分配释放；列尺度只读保留到全部批次结束。

精度复核：先 INT32 转 FP32，再乘行尺度，再乘列尺度，运算顺序保持；原尺度除法修复、零行 scale=1、量化除法、近半值修复及 ODD/RINT 转换保持。所有行宽对齐门控保证多行连续搬运与每行 UB/GM 地址合法；比较的填充尾元素初始化，在正常有限输入路径中，整数转换前按原流程裁剪到目标范围。CPU 调度模型和旧 API 源码保持不等于硬件 Div、编译器或异常浮点值行为得到实机证明。

风险：按批尺度修复会多次调用精度辅助链；输入深度从双缓冲降为单缓冲，可能失去预取重叠；每批标量尺度数组与逐行归约可能仍造成 Scalar 开销。仅凭逻辑搬运从 13MN 降至 9MN，不能推出固定加速倍数或总分。

### v139：一次融合核中的二维 Cube 分块

旧路径按 M 分配 Cube，每组计算全 N。新路径对一类小 M、大 N 的形状按 M/N 建立核网格。每个 AIC 只生产对应的 C 列片段；全部 AIC 和 AIV 在同一处硬 `SyncAll<false>()` 后，AIV 按完整行的唯一归属执行原量化助手。整行尺度始终来自全部 N，没有用列片段尺度冒充整行尺度，也没有跨核浮点 atomic 或自建忙等。

资源门控按 `min(availableCoreNum, physicalAIC, physicalAIV/2)` 限制网格，并保持一次 launch。小 M 行块请求为 16 或 32；列片宽按 128 对齐。只有返回的 singleCoreM/N 与请求一致才进入新路径，否则回退。A、B 和 C 地址分别为 `row*K`、`column*K`、`row*N+column`；`SetOrgShape(m,n,k,k,n)` 显式保持完整 C 行距。所有参与核在屏障前都没有提前 return/continue，Matmul End 位于屏障之前。对 16×8192×512 的代理请求，新核网格明显扩大；这不等于已经确认 Judge 隐藏点命中该分支。

该路线依据 [CANN 9.0 SyncAll 文档](https://www.hiascend.com/doc_center/source/en/CANNCommunityEdition/900/API/ascendcopapi/atlasascendc_api_07_0204.html) 的 A3 混合硬同步支持，并使用批调度限定。源码与几何模型能证明请求网格、整行归属和不跳过屏障，不能证明编译器、Matmul 内部状态、实际调度及硬件完成顺序。

风险：全局屏障会取消旧两块 M 的 Cube/Vector 重叠，批调度可能增加排队，小 M 仍只有少数 AIV 有整行可处理。实际分片写回的行距、B 转置模板和新增内核语法需要 CANN 编译及设备验证。原主机静态 workspace 缓存被保留；它未按 context/stream 隔离，不能据此宣称支持多流并发安全。
