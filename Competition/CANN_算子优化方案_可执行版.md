## 2. 当前算子已有优化与剩余问题

对照基线 `baseline/kernel.asc`：

- 小矩阵已经走 Vector 直接点积及本核量化；通用路径使用 Cube 与 Vector 融合；矩阵乘已用 `CFG_MDL`。
- 通用后处理已用两块 workspace 缓冲，并在当前块计算前预取下一块。
- `N>=32 && N<=3072 && N%32==0` 已启用最多四行合批；实际批量还受 6144 元素容量限制。
- 列向量 `x2Scale` 已在每个 N tile 内跨行复用，但第一遍求行最大值和第二遍量化仍各加载一次。
- 通用路径还两遍读取 INT32 workspace，两遍 Cast 及反量化；半整数筛选与修正形成较长指令链。
- 主路径有三组长度 64 的标量预取数组；tiny 路径仍逐行取出点积结果、标量反量化、写回激活。

这些是源码观察，不足以判定实际瓶颈。现有设备证据为 v84 的 15/15 通过及单次耗时；尚无真实 shape 和流水剖析。

## 3. 优先落地 A：列尺度跨两遍复用

### 改哪里

函数：`quant_matmul_relu_quant_vector`。完整候选：[kernel.asc](候选_列尺度复用/kernel.asc)；精确补丁：[source.diff](候选_列尺度复用/source.diff)；审查记录：[review.json](候选_列尺度复用/review.json)。

基线 SHA256：`b45baa5babfce9522491e50709ea62908728208fb38aff44eb1aeb1a77317107`。

候选 SHA256：`2c592c5571baad502e55d5157d954e8bb1bbc2c6c222e0a0a12a213499320851`。

### 改动机制

当 `N<=3072` 时，第一遍将 `x2Scale` 搬进原有队列并出队；第一遍结束保留这块已分配的缓冲，第二遍直接读同一 LocalTensor，最后释放。其余 N 保留原搬运与释放流程。

这是官方 Gamma 预加载方法的具体迁移，区别是当前列尺度已经按 tile 跨行复用，新增优化只消除第二遍的重复加载：

```text
原流程：加载列尺度 → 求行最大值 → 释放
        加载列尺度 → 量化输出 → 释放

候选：  加载列尺度 → 求行最大值 → 保留
        复用列尺度 → 量化输出 → 释放
```

本工程 `kVectorTileN=6144`，因此选定的 `N<=3072` 范围一定只有一个 N tile。3072 是保守试验门控，不是 UB 极限；暂不扩大范围，便于单独判读。

### 收益和资源

- 命中门控时，每次该 Vector 函数调用减少一份 `4*N` 字节的 GM 读取，并省掉第二次队列分配、入队和出队。
- 使用现有 `x2ScaleQueue`，新增 UB 字节为 0；延长其存活期，不更改其他缓冲的分配。
- 仍然两遍读取 workspace，收益不能按“全部后处理搬运减半”计算。
- 对 N 很小或其他流水占主导的形状，节省量可能很小；额外分支与编译布局也可能抵消收益。

### 等价性条件

输入列尺度在核函数执行期间只读，并且不与输出存储重叠；使用前按题目接口确认这一点。缓存保留第一次 DataCopyPad 后的相同 FP32 位模式，包括相同填充值。两遍计算的 Cast、两次反量化乘法顺序、归约、除法、半整数修正、RINT 和输出转换均保持。

第一遍 DeQue 已完成输入就绪同步；缓冲在第二遍消费结束前不释放，也不被其他队列占用。第二遍结束只 Free 一次，未缓存路径仍每 tile 各 Free 一次。

### 已检查与待检查

已检查：修改限于该函数的列尺度加载及所有权管理；所有 InitBuffer、数值 API 调用序列和屏障数量保持；N=1…13000 的缓冲所有权模型无重复释放、漏释放或多块同时占用。

待检查：CANN 编译、NPU 实际正确性、队列和编译资源、性能。所有权模型是 CPU 静态辅助检查，不是设备验证。

设备验证至少覆盖 N=1/7/8/31/32/33/64/3071/3072/3073/6144/6145，配合 1/2/3/4/5/63/64/65 行及实际分核尾行；tiny 有独立旁路，必须确认测试确实进入修改后的通用函数。比较输出 int8 及 yScale 的原定精度。性能用相同数据、环境和口径比较候选与 v84，按逐点结果决定保留，不能只看总耗时。

## 4. 优先落地 B：收缩 Scalar 预取窗口

**来源：**Scalar 优化文档中的 Load/Store、存活期与动态数组分析。迁移到当前代码时，可将 `kPairPrefetchSpan=64` 单独试为 16；必要时另做 8 的独立候选。

**改动位置：**同一 Vector 函数的 `pairX1Prefetch`、`pairX1Prefetch2`、`pairRowScalePrefetch`。第二遍两组数组的源级容量由合计 512B 降到 128B；实际是否减少寄存器 spill 必须看编译与流水数据。

**条件：**窗口需为现有批量上限 4 的倍数。必须保持两个 pass 的 group 循环、nextRows 预取及奇数尾行相互一致；不能只改数组长度而不改迭代跨度。数值、GM 布局、批量上限和 UB 分配保持。

**收益假设：**降低热路径的栈与 Load/Store 压力。可能代价是增加分组循环次数、破坏原先长窗口预取收益；是否提速未知。本次已给出具体改法，未生成该候选，避免与 A 混在同一次实验。

## 5. 更大改动的实施方案与前置条件

### 5.1 Vector 反量化与归约链融合

将 `Cast → 行尺度乘法 → 列尺度乘法 → 行最大值` 合为一次批量计算，让中间值尽量留在寄存器；行尺度在计算内部广播，列尺度跨行复用。参考已读的 `tail_axis_2_distbrc.asc` 和 `reduce_max_ar_unroll.asc`。

迁移约束：当前数值路径要求两次 FP32 乘法按原顺序舍入，不能改成先乘两个 scale；各行最大值独立。全负行仍按 ReLU 后最大值为零处理。涉及 NaN、Inf、subnormal、尾块填充与 mask 时，按现有回退及赛题规则验证。

这个方案不是直接把 950 RegAPI 粘到当前工程：先确认目标是否支持所需寄存器接口；不支持时用当前 API 压缩调用或减少重复步骤。历史 v83 已试过 tiny 的两次向量乘法替换，整体未改善，原样重复不算新方案。

### 5.2 完整行激活驻留

候选目标是减少第二遍 workspace 读取和重复反量化。需要同时保存完整行的激活及后续精确量化所需原值；按互斥阶段复用缓冲时，每个覆盖必须证明上一阶段已结束。只对完整行可放入资源预算的 shape 使用，其他 shape 完整回退。

必须先读历史单遍 / 缓存实验：已有路线未取得明确收益，不能把“单遍一定更快”当结论。只有提出新的资源布局、缩短具体指令链或解决已有退化原因，才生成候选。

### 5.3 Cube 的输入复用与尾轮负载均衡

SWAT 用窗口及 Z 字形改变 M/N 工作块访问顺序，提高输入复用；尾轮策略降低末轮少数核工作过重的问题。当前代码按 M 分组、每组处理完整 N，并用固定跨核 flag 配合 Vector。完整迁移需要重写调度和对应生产消费关系，单改一个 tile 常量不能实现官方方案。

实施前记录实际 M/N/K、AIC/AIV 分组、每核块数和尾轮空闲；在保持合法 INT8→INT32 累加的前提下，评估 baseM/baseN/baseK、L1 和 L0 容量。先修改分配及输入复用，保留确定的行级结果就绪条件；不能让 Vector 在部分 N 尚未完成时计算整行尺度。

历史 v90 已试 M/N 分核加两个串行 kernel，15/15 但未提升总体观测。新增方案要解决它失去融合重叠和额外启动的成本；不可原样重试。

### 5.4 双缓冲、UnitFlag 与 SplitK

已有 workspace 双缓冲；只有剖析确认等待搬运明显且资源足够时再增深度。官方 UnitFlag 示例属于特定 MMAD / FIXPIPE 路径，不能代替当前 Cube/Vector 跨核 Set/Wait。

SplitK 更适合 M/N 工作块少而 K 长的情况，会增加部分结果 workspace 与合并。当前按行求最大值和再量化必须等待最终完整 C；应先完成全部 K 累加，再反量化和求尺度。不能把已反量化的各段浮点结果随意相加，或默认浮点 atomic 的次序等价。未取得实际形状和设备支持前，将其保留为条件方案。
